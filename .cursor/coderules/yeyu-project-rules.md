# 夜语（YeYu）项目开发规范

## 🎯 项目数据规范

### 1. 数据结构规范
- **数据验证要求**：
  - 所有字段在保存前必须进行类型和范围验证
  - 内容长度必须在允许范围内
  - 数值范围必须在有效区间内（情绪值：0-10）
  - 文本长度限制：发布内容和评论内容最大 300 字

### 2. 相似度计算规范
- 必须使用标准算法计算情绪相似度
- 相似度结果必须归一化到 0-1 范围
- 算法实现必须可测试、可验证
- 算法返回时间必须 < 2秒

---

## 🚀 功能流程规范

### 3. 发布流程规范
- **步骤限制**：发布流程必须 ≤ 3 步
- **响应时间**：UI 交互响应时间必须 < 200ms
- **用户引导**：流程必须清晰，用户操作路径最短
- **输入验证**：每个步骤必须验证输入有效性
- **发布成功率**：必须达到 100%（包含错误处理和重试机制）

### 4. 内容安全规范
- **强制要求**：所有内容发布前必须通过 `msgSecCheck` 安全检测
- **失败处理**：安全检测失败时必须拒绝发布，不允许绕过
- **用户提示**：检测失败时必须给出明确的用户提示
- **错误处理**：检测服务异常时必须有降级策略（默认拒绝）
- **敏感内容屏蔽成功率**：必须 > 95%

### 5. 匿名化处理规范
- **ID 生成**：匿名ID生成必须使用不可逆哈希算法
- **唯一性**：同一用户必须生成相同的匿名ID
- **隐私保护**：匿名ID无法反向推导用户真实身份
- **数据存储**：
  - ✅ 允许存储：`anonymousId`, `emotion`, `content`, `timestamp`
  - ❌ 禁止存储：`openid`, `userInfo`, `phoneNumber`, `realName`
- **数据验证**：定期检查数据存储，确保不包含真实身份信息

---

## ⚡ 性能规范

### 6. 算法性能要求
- **相似度推荐**：算法返回结果必须 < 2秒（100条数据场景下）
- **查询优化**：查询必须使用索引，限制查询数量，避免全表扫描
- **计算位置**：复杂计算应在服务端执行，避免客户端计算
- **性能测试**：必须测试边界情况下的性能表现

### 7. 交互性能要求
- **UI响应**：所有用户交互响应时间必须 < 200ms
- **加载状态**：异步操作必须显示明确的加载状态
- **列表性能**：长列表必须优化渲染性能，使用虚拟列表或分页加载

---

## 💬 功能实现规范

### 8. 共鸣流实现规范
- **推荐算法**：必须基于情绪相似度进行推荐
- **排序规则**：推荐结果必须按相似度降序排序
- **数量限制**：单次加载数量限制为 20 条
- **分页加载**：列表必须支持分页和上拉加载更多
- **数据同步**：
  - 页面进入（`onShow`）时自动同步最新数据
  - 支持下拉刷新手动同步数据
  - 每次调用返回最新数据，确保数据一致性

### 9. 互动功能规范
- **乐观更新**：用户交互必须立即更新UI，后台异步处理
- **错误回滚**：后台操作失败时必须回滚UI状态
- **防重复点击**：必须防止用户重复快速点击造成重复操作
- **反馈机制**：所有互动操作必须有明确的视觉反馈
- **本地更新**：点赞和评论操作后，仅更新本地数据，无需重新请求整个列表

---

## 📊 数据统计规范

### 10. 数据采集规范
- **隐私保护**：统计数据中不得包含用户真实身份信息
- **关键指标**：必须采集发帖量、共鸣率等关键指标
- **采集时机**：关键用户行为必须实时采集
- **容错机制**：数据采集失败不得影响主业务流程

### 11. 统计接口规范
- **接口设计**：统计接口必须支持按日期、时间段查询

---

## 🛡️ 安全规范（强制执行）

### 12. 内容安全规则
1. **所有用户输入必须经过 `msgSecCheck`**
2. **检测失败时拒绝发布，不允许绕过**
3. **敏感内容必须立即屏蔽**

### 13. 隐私保护规则
1. **数据库中不存储 `openid`、`userInfo`、`phoneNumber` 等实名信息**
2. **匿名ID生成使用不可逆哈希算法**
3. **数据访问遵循最小权限原则**

---

## 🧪 测试规范

### 14. 开发测试要求（强制执行）
- **每一步开发完成后必须立即测试，不得跳过或延迟**
- 开发流程：开发功能 → 立即测试功能 → 修复问题 → 继续下一个功能
- 不能等到所有功能开发完成后再测试
- 功能开发完成后必须进行完整的功能测试
- 性能优化后必须验证性能指标是否达标
- **测试是开发的一部分，不是额外的步骤**

### 15. 测试内容要求
- **功能测试**：
  - 测试所有用户交互流程（正常场景、异常场景）
  - 测试边界条件（空内容、超长内容、极端情绪值）
  - 测试数据验证是否生效
  
- **安全测试**：
  - 测试匿名化是否真正保护隐私
  - 测试权限控制是否生效
  
- **性能测试**：
  - 测试发布流程响应时间是否 < 200ms
  - 测试相似度算法返回时间是否 < 2秒（100条数据场景）
  - 测试列表滚动流畅度
  - 测试页面加载时间
  
- **兼容性测试**：
  - 测试不同微信版本兼容性
  - 测试不同设备屏幕适配（iOS、Android）

### 16. 测试环境要求
- 必须测试不同网络环境


---

## 📚 开发文档规范（强制执行）

### 17. 开发记录要求
- **文档创建**：每实现一步开发，都必须创建对应的 Markdown 文件进行规范的记录
- **记录内容**：
  - 实现的功能点描述
  - 技术实现方案和关键代码片段
  - 遇到的问题和解决方案
  - 测试验证结果
  - 性能指标达成情况
- **文件命名**（强制执行）：
  - **必须使用 plan.md 中的步骤编号**：文档命名必须遵循 `plan.md` 中的步骤编号格式（如 `1.1`、`1.2`、`2.1`、`2.2` 等）
  - **命名格式**：`docs/development/[步骤编号]-[功能名称].md`
  - **示例**：
    - `docs/development/11-项目环境搭建.md`（对应 plan.md 中的 1.1）
    - `docs/development/12-基础架构开发.md`（对应 plan.md 中的 1.2）
    - `docs/development/21-情绪滑盘组件开发.md`（对应 plan.md 中的 2.1）
    - `docs/development/22-文本输入组件开发.md`（对应 plan.md 中的 2.2）
  - **编号规则**：
    - 将 plan.md 中的步骤编号（如 `1.1`、`1.2`）去掉小数点，直接拼接为文件编号
    - 阶段一：`1.1` → `11`、`1.2` → `12`、`1.3` → `13`
    - 阶段二：`2.1` → `21`、`2.2` → `22`、`2.3` → `23`、`2.4` → `24`
    - 阶段三：`3.1` → `31`、`3.2` → `32`、`3.3` → `33`、`3.4` → `34`
    - 阶段四：`4.1` → `41`、`4.2` → `42`、`4.3` → `43`、`4.4` → `44`、`4.5` → `45`、`4.6` → `46`、`4.7` → `47`
    - 阶段五：`5.1` → `51`、`5.2` → `52`
    - 阶段六：`6.1` → `61`、`6.2` → `62`、`6.3` → `63`
    - 阶段七：`7.1` → `71`、`7.2` → `72`、`7.3` → `73`、`7.4` → `74`
    - 阶段八：`8.1` → `81`、`8.2` → `82`、`8.3` → `83`
  - **命名要求**：编号必须与 plan.md 中的步骤编号一一对应，便于追溯和查找
- **文档位置**：统一存放在项目文档目录中，便于查找和溯源
- **更新时机**：功能开发完成后立即记录，不得延迟或遗漏
- **溯源价值**：文档记录必须能够完整还原开发过程和决策依据

### 18. 文档规范要求
- **结构清晰**：文档必须包含必要的章节结构（功能描述、实现方案、测试结果等）
- **内容完整**：关键信息必须记录完整，包括代码变更、配置变更等
- **便于检索**：使用清晰的标题和关键词，便于后续查找
- **版本记录**：重要变更必须记录版本和时间戳

### 19. 进度跟踪要求（强制执行）
- **plan.md 更新必须**：每实现一项功能，都必须在 `plan.md` 中的相应项打勾（`[ ]` 改为 `[x]`）
- **更新时机**：功能开发完成并测试通过后立即更新，不得延迟或遗漏
- **更新范围**：
  - 必须更新对应的功能项（如实现了"实现瓶子容器"，就要在对应的 `[ ]` 中打勾）
  - 必须更新对应的测试项（如完成了"测试瓶子点击打开 CreateMessageCard"，就要在对应的测试项中打勾）
  - 必须更新对应的阶段综合测试项（如完成了阶段二的所有功能，就要在"阶段二综合测试"中更新相应的测试项）
- **更新方式**：
  - 在 `plan.md` 中找到对应的任务项
  - 将 `[ ]` 改为 `[x]` 表示已完成
  - 确保勾选的项目与实际完成的功能一致
- **验证要求**：
  - 提交代码前必须检查 `plan.md` 是否已更新
  - 确保已完成的功能都已正确标记
  - 确保未完成的功能仍然标记为 `[ ]`

## ✅ MVP 范围边界

### 必须实现的功能
- 情绪滑盘选择（价度×唤醒度，0-10范围）
- 文字内容发布（≤300字）
- 相似度推荐算法（返回时间 < 2秒）
- 共鸣互动功能（点赞、评论）
- 内容安全检测（`msgSecCheck`）
- 数据同步机制（页面进入自动同步、下拉刷新、上拉加载）

### 暂不实现的功能（明确边界）
- AI自动回复
- 语音/图片/视频输入
- 用户关系链和私信
- 心理诊断功能
- 商业化模块

## 🚨 关键提醒（强制执行）

1. **安全第一**：内容安全和隐私保护是最高优先级
   - 所有用户输入必须经过 `msgSecCheck`
   - 不存储真实身份信息，使用不可逆哈希生成匿名 ID
   
2. **性能要求**：所有性能指标必须达标
   - UI 响应 < 200ms
   - 算法返回 < 2秒
   - 不能因为时间紧迫而降低性能要求
   
3. **测试必须**：每步开发后必须立即测试，不得跳过或延迟
   - ✅ 正确做法：开发功能 A → 立即测试功能 A → 修复问题 → 开发功能 B
   - ❌ 错误做法：开发功能 A、B、C → 最后统一测试
   
4. **文档记录必须**：每实现一步开发，都要创建 MD 文件进行规范的记录，方便溯源
   - ✅ 正确做法：开发功能 A → 立即测试 → 创建文档记录 → 继续下一个功能
   - ❌ 错误做法：开发完成后才补充文档，或遗漏文档记录
   - **文档命名必须遵循 plan.md 步骤编号**：文件命名必须使用 plan.md 中的步骤编号（如 `1.1` → `11`、`1.2` → `12`、`2.1` → `21`），格式为 `docs/development/[步骤编号]-[功能名称].md`
   - **示例**：`docs/development/11-项目环境搭建.md`（对应 plan.md 1.1）
   
5. **进度跟踪必须**：每实现一项功能，都必须在 `plan.md` 中的相应项打勾（`[ ]` 改为 `[x]`）
   - ✅ 正确做法：开发功能 A → 测试通过 → 在 plan.md 中打勾 → 继续下一个功能
   - ❌ 错误做法：开发完成后才更新 plan.md，或遗漏进度更新
   - **更新时机**：功能开发完成并测试通过后立即更新，不得延迟或遗漏
   - **更新范围**：必须更新对应的功能项、测试项和阶段综合测试项
   
6. **代码质量**：遵循 Clean Code 原则，保持代码整洁
   - 即使时间紧迫，也要保持代码整洁和规范
   - 代码必须通过 ESLint 检查
   
7. **边界明确**：严格遵循 MVP 范围，避免功能蔓延
   
8. **常见陷阱避免**：
   - 不要频繁调用 setData（合并更新）
   - 不要忘记处理错误（所有调用都要 try-catch）
   - 不要忽略权限配置
   - 不要绕过安全检测（必须通过检测才能发布）
   - 不要等到所有功能开发完成后再进行测试
   - 不要遗漏开发文档记录（每步开发后必须立即记录）
   - 不要随意命名开发文档（必须使用 plan.md 中的步骤编号，如 `1.1` → `11`）
   - **不要遗漏 plan.md 进度更新**（每实现一项功能后必须立即在 plan.md 中打勾）
